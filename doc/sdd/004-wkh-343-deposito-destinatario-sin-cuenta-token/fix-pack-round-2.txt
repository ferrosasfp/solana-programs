2. BLQ-BAJO-3 — el tercer desenlace del reloj ya no se colapsa en el $?
-----------------------------------------------------------------------------
`cluster_now()` devolvia TRES estados para el slot y DOS para el timestamp: si
`getBlockTime` daba `null`, sustituia el reloj LOCAL y seguia. Todos los veredictos
de deadline son comparaciones contra ese numero.

MEDIDO con el MISMO escrow y el MISMO codigo, moviendo una sola cosa. El escrow es
FABRICADO byte a byte en el layout del programa y servido por un `rpc` stubeado
(en devnet no hay ninguno `Deposited` y vencido: los 10 son terminales); lo que es
real es `main()` sin tocar. El deadline cae ENTRE los dos relojes: pasado para el del
cluster, futuro para el local.

    script ENTREGADO
      getBlockTime ok   -> "REFUND-ONLY: the release window closed at ..."   exit 1
      getBlockTime null -> "live, still inside its release window"           exit 1
                           razon: "the CLUSTER CLOCK was not read, so every deadline
                           verdict above compares against this host's local clock"

    CONTRAFACTUAL: la misma corrida con la condicion del reloj desactivada
      getBlockTime ok   -> "REFUND-ONLY: ..."                                exit 1
      getBlockTime null -> "live, still inside its release window"           exit 0  <- el defecto

O sea: el veredicto sigue cambiando —el script no puede saber la hora real— pero ya
NO sale 0. El humano veia el aviso `[LOCAL clock]` en el encabezado; el `$?` no, y el
`$?` lo volvi portante en la ronda 1. `cluster_now` devuelve ahora un cuarto valor,
`trusted`. Cuando el slot SI se leyo y solo fallo el block time se conservan las dos
cosas: el slot sigue estampando la salida y `trusted` queda en False.

Ninguno de los dos casos es exotico: `getBlockTime` devuelve `null` en slots
podados o no rooteados de un endpoint publico, y un reloj de contenedor que deriva
es lo normal.
